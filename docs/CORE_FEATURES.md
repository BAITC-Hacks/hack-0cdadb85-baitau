# Core Recommendation Features

Публичная функция: `core.generator.run_pipeline(request, contractors) -> dict`.
Core принимает подготовленный каталог `list[dict]` с уникальными ID и запрос
по существующему контракту. Описанное поведение проверено regression-тестами.

## Pipeline

1. Hard filters: выбрать город и категорию, проверить остальные ограничения.
2. Deterministic scoring: вычислить score для прошедших фильтры кандидатов.
3. Ranking: отсортировать по убыванию score, затем по возрастанию начальной цены и ID.
4. Top-3: вернуть максимум трёх подходящих подрядчиков.
5. Explanations: сформировать объяснение по фактам профиля и запроса для каждой карточки.

## Hard filters

- `city`: точное совпадение города.
- `category`: запрошенная категория присутствует в `categories`.
- `busy_dates`: запрошенная дата отсутствует в календаре занятости профиля.
- `event_format`: формат присутствует в `event_formats`.
- Budget: `price_from_kzt <= budget_kzt`.
- Language: если язык задан, он присутствует в `languages`.
- Duration: если длительность задана и `max_hours` известен,
  `max_hours >= duration_hours`.
- `max_hours=None` не является автоматическим отказом: такой профиль проходит
  проверку длительности при соблюдении остальных условий.

Сравнение города, категории, формата и языка точное, с учётом регистра.

## Statuses

- `matched`: после фильтров остался хотя бы один кандидат.
- `no_category_in_city`: в исходном каталоге нет сочетания города и категории.
- `no_eligible_candidates`: сочетание города и категории есть, но все кандидаты
  отклонены остальными условиями.

Для `no_eligible_candidates` возвращаются счётчики `busy_on_date`, `over_budget`,
`unsupported_format`, `unsupported_language`, `duration_too_long`.
Один профиль может учитываться в нескольких причинах отказа.

## Marketplace compatibility

Core обрабатывает base и `USR-*` профили одинаково: специальной логики
по происхождению или префиксу ID нет. Пользовательский подрядчик использует
тот же contractor contract, что и базовый профиль.

`helpers.utils.load_all_contractors()` передаёт объединённый каталог:
66 базовых профилей плюс сохранённые feature profiles. Проверена цепочка
сохранения через `save_feature_contractor()`, повторной загрузки и подбора
из 67 профилей. Конкурентоспособный пользовательский профиль попадает в top-3
при соблюдении фильтров; добавление само по себе не гарантирует место в выдаче.

Флаги `synthetic`, `city_imputed`, `price_imputed` сохраняются в карточке результата.
В частности, `synthetic=True` пользовательского профиля доходит до output.

## Determinism

При одинаковом запросе и данных каталога порядок результатов и score стабильны.
Проверены пять повторных запусков, повторная загрузка сохранённого каталога
и reversing catalog: обратный порядок входных профилей не меняет результат.
При равных score порядок определяется ценой и уникальным ID.

## Availability

Наличие даты в `busy_dates` исключает подрядчика до ранжирования, включая `USR-*`.
Изменение даты может изменить выдачу. В базовом демо-запросе
(Алматы, Фотограф, свадьба, 400000 ₸, 8 часов, русский)
`HK-76268` присутствует 2026-11-14 и исключается 2026-11-15 из-за занятости.
Отдельный тест подтверждает причину: удаление только занятой даты из тестовой
копии профиля возвращает кандидата в выдачу.

## Explainability

Объяснение формируется детерминированно по фактам профиля и запроса:
город, категория, формат, дата, начальная цена, бюджет и запас к начальной цене.
Язык и длительность упоминаются, когда пользователь задал эти параметры.
При `max_hours=None` объяснение сообщает об отсутствии указанного почасового
лимита, не обещая конкретную длительность работы.

Generic-only explanations вроде «Отличный выбор» не используются.
Проверено, что объяснение пользовательского профиля содержит его фактическую
цену, язык и длительность, а также дату, формат и бюджет запроса.
Цена «от» и запас к ней не означают подтверждённую итоговую стоимость заказа.

## Regression coverage

Проверки находятся в `core/test_generator.py`, `core/test_catalog.py`,
`core/test_marketplace.py` и интеграционных тестах helpers:

- Marketplace contractor in top-3 при каталоге 66 + 1, включая сохранение
  и повторную загрузку через реальные функции helpers.
- Busy date exclusion для базовых и пользовательских профилей.
- Synthetic propagation и сохранение остальных флагов происхождения данных.
- Diagnostics: учёт всех причин отказа и сохранение трёх статусов.
- `fallback=False` при штатном вызове настоящего Core через `safe_pipeline_call()`.
- Детерминизм повторных запусков и независимость результата от порядка каталога.
- Все hard filters и отсутствие автоматического отказа при `max_hours=None`.

Тесты сохранения используют временное feature-хранилище и не добавляют профили
в рабочий каталог приложения.

Запуск полного набора проверок из корня проекта:

```bash
python -m unittest discover -v
```
